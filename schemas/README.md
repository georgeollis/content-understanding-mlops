# Content Understanding Schemas (local reference + validation)

This folder gives you two things:

1. **`analyzer.schema.json`** — a real, enforceable JSON Schema for the analyzer definition files
   at `../analyzers/*/analyzer.json` (the request body sent by `../scripts/upload-analyzers.ps1`).
2. **`build-analyzer-schema.ps1`** — the tool that generates `analyzer.schema.json` from the
   **official, authoritative source**: Microsoft's published Swagger/OpenAPI spec for Content
   Understanding, not hand-written or guessed.

## Where this comes from (source of truth)

- Repo: [`Azure/azure-rest-api-specs`](https://github.com/Azure/azure-rest-api-specs)
- Path: `specification/ai/data-plane/ContentUnderstanding/stable/2025-11-01/ContentUnderstanding.json`
- This is a Swagger 2.0 file **auto-generated from Microsoft's TypeSpec source** (the actual
  model definitions engineers write against internally), so it's the same contract the real
  Content Understanding service enforces — not a blog post or an LLM's memory of the API.

`build-analyzer-schema.ps1` walks that file's `$ref` graph starting from `ContentAnalyzer` and
pulls in every transitively-referenced definition (`ContentFieldSchema`, `ContentFieldDefinition`,
`ContentFieldType` enum, `ContentAnalyzerConfig`, `KnowledgeSource`, etc.), strips server-only
read-only properties (`analyzerId`, `status`, `createdAt`, ...) that authors shouldn't set locally,
and writes a single self-contained JSON Schema file.

## How this enforces "semantic conventions" for schema authors

Anyone authoring or updating a family's `analyzers/<family>/analyzer.json` gets real
validation, not just tribal knowledge:

- **Correct field types only** — `type` must be one of `string`, `date`, `time`, `number`,
  `integer`, `boolean`, `array`, `object`, `json` (typos like `"currency"` are rejected).
- **Correct generation method** — `method` must be `extract`, `classify`, or `generate`.
- **Correct processing location** — `processingLocation` must be `geography`, `dataZone`, or
  `global`.
- **Correct analyzer ID pattern** — `baseAnalyzerId` must match `^[a-zA-Z0-9._-]{1,64}$`.
- Nested `array`/`object` field definitions (`items`, `properties`) are recursively validated the
  same way.

### Editor validation (VS Code)

`../.vscode/settings.json` maps every `analyzers/*/analyzer.json` file to this schema via
`json.schemas`, so VS Code shows red squiggles + autocomplete for `type`/`method`/
`processingLocation` etc. as you type — no per-file `"$schema"` property needed (which would
otherwise get sent to the API as an unrecognized field when uploaded).

### Command-line / CI validation

All PowerShell scripts, runnable per-family or with `-All`:

- **`validate-analyzers.ps1`** — validates every `analyzers/<family>/analyzer.json` against
  `analyzer.schema.json` (catches bad `type`/`method`/`processingLocation` values, etc.).
- **`build-ground-truth-schema.ps1`** — derives `analyzers/<family>/golden/expected.schema.json`
  directly from that family's `analyzer.json` `fieldSchema`. Re-run it whenever you add/rename/
  remove a field so ground-truth files stay in lockstep with the analyzer.
- **`sync-golden-fields.ps1`** — when `fieldSchema` changes, patches every `expected.json` in a
  family's `golden/` with placeholder values for newly-required top-level fields (deliberately
  wrong-typed for non-string fields, so `validate-golden.ps1` keeps failing until a human fills
  them in) and warns about fields no longer in the schema. Top-level fields only.
- **`build-golden-manifest.ps1`** — writes `analyzers/<family>/golden/manifest.json`: a sha256
  checksum of every source document (any supported format - PDF, DOCX, XLSX, PPTX, images, and
  more; see `scripts/lib/GoldenDocs.ps1`) / `*.expected.json` pair in the golden set, plus a
  `groundTruthSource` flag (`generated` vs. `human-verified`). Re-run it after adding/removing/
  editing golden docs.
- **`validate-golden.ps1`** — the CI-facing check: confirms every golden doc matches its checksum
  in `manifest.json` (catches silent edits/corruption/stale manifests), every `expected.json`
  conforms to `expected.schema.json` (catches typo'd/renamed fields that would otherwise silently
  score as "missing" in `compare-analyzers.ps1`), that every top-level `fieldSchema` field is
  present (no missing/extra fields), and that no unreviewed `"_bootstrap"` draft marker remains
  (see `scripts/bootstrap-golden.ps1`).
- **`list-families.ps1`** — scans `analyzers/*` (excluding any `_`-prefixed folder, e.g.
  `_template`) and regenerates the family index table in `analyzers/README.md` with
  `-WriteReadme`; `ci-check.ps1` fails if the committed table is stale.

All scripts require PowerShell 7+ (`pwsh`) and exit non-zero on failure, so they're usable as a
pre-commit hook or CI gate before `promote-analyzer.ps1` runs. No Python or external packages
required.

Note on ground truth: `expected.json` files generated by a family's own sample-document generator
(when one exists, e.g. a template script) are self-referential ground truth - they prove the
analyzer can read back what a template wrote, not independent accuracy. Treat
`groundTruthSource: "generated"` docs as smoke tests; mark a doc `"human-verified"` in
`manifest.json` only once someone has checked its `expected.json` against the real source document.

## Re-generating the schema

If Microsoft ships a newer API version (check
[`specification/ai/data-plane/ContentUnderstanding/`](https://github.com/Azure/azure-rest-api-specs/tree/main/specification/ai/data-plane/ContentUnderstanding)
for `stable/<version>` or `preview/<version>` folders):

1. Update `$swaggerUrl`/`$rootDefinition` in `build-analyzer-schema.ps1` if the version/path changed.
2. Delete the cached copy so it re-downloads: `Remove-Item "$env:TEMP\ContentUnderstanding.swagger.json"`.
3. Run `pwsh -File .\build-analyzer-schema.ps1` (it auto-downloads the new spec to `%TEMP%` if missing).
4. Re-run `pwsh -File .\validate-analyzers.ps1` (or open the analyzer files in VS Code) to confirm
   existing analyzer definitions still validate against the new schema.
